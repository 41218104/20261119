10
拆解原則：什麼樣的任務適合並行？
✔ 適合並行
彼此獨立，不需要等別人的結果
只讀取，或各自寫不同的檔案
輸出格式可以事先約定好
例子
分析多個資料夾、比較多個套件、多語系翻譯、產生多組測試資料
✘ 不適合並行
有先後相依（先設計 API 才能寫前端）
會同時修改同一個檔案
需要頻繁來回討論、反覆修改
例子
重構同一個模組、資料庫 migration、修改共用設定檔
口訣：
可切分、不相依、格式先約定 —— 三個條件都成立，才值得開多個子代理

===== 第 12 頁 =====
多 
Subagent 
並行運作的威力
12
並行不是免費的：四個注意事項
1
Token 成本倍增
N 個子代理 ≈ N 份 context 的花費。可替子代理指定較便宜的 model；沒有指定時，會沿用主 session 的模型。
2
寫入衝突
多個子代理同時改同一個檔案會互相覆蓋。並行任務盡量唯讀，或明確切分每個人負責的檔案範圍。
3
限制步數
用 steps 設定上限，避免子代理陷入無限迴圈；到最後一步時，它會被要求直接用文字總結。
4
交代清楚
子代理從全新的 context 開始，看不到你和主 Agent 的對話。Prompt 要給足背景與輸出格式。
課堂練習：
同一個任務，分別用「單一 Agent」與「3 個 Subagent」執行，記錄花費時間與 token，下週分享結果。

===== 第 24 頁 =====
讓多個 
Subagent 
來組成專業團隊
24
帶團隊的五個心法
1
交接靠檔案，不靠記憶
spec.md、handoff.md 讓全新 context 的子代理也能接手
2
一人一職
角色越單純，description 越清楚，主 Agent 越不會派錯人
3
審查與實作分離
reviewer 沒有編輯權，才不會「自己出題、自己改考卷」
4
設定迴圈上限
prompt 寫「最多 3 輪」，frontmatter 設 steps，雙重保險
5
人類保留最後決策
重要變更仍由你 review 之後才 commit / merge
